核对日期：2026-11-04（北京时间）。实施基线：`wlj2333-wq/loon-adblock@03ccc1408a3254419e0421813e41b3aac89def5e`，插件 v1.3.2，播放页脚本 v1.3.0。

## 公开字段先例

| 字段及接口 | 可核对来源 | 证据能说明什么 |
| --- | --- | --- |
| GET `api.live.bilibili.com/xlive/app-room/v1/index/getInfoByRoom` 的 `data.activity_banner_info` | [blackmatrix7 历史脚本固定版本](https://github.com/blackmatrix7/ios_rule_script/blob/593a8466ae434b4d5d969cf758e5050aabc10677/script/archive/bilibili/bilibili_plus.js)，搜索“直播去广告” | 旧脚本曾在该接口将活动横幅信息设为 null；文件位于 archive，不是当前手机仍有效的证据 |
| 同一 app-room/v1 房间信息接口的 `data.shopping_info.is_show` | [yaoyaole0112 公开规则固定版本](https://github.com/yaoyaole0112/surge/blob/72313cba3f509266317779c75207a1263d64976a/sgmodule/Ads/%E5%B9%BF%E5%91%8A%E6%8B%A6%E6%88%AA%E5%87%80%E5%8C%96%E5%90%88%E9%9B%86.sgmodule)，搜索 `shopping_info` | 发布者的 jq 规则明确覆盖 app-room/v1/getInfoByRoom，并把展示标志设为 0；这是第三方处理先例，不是官方协议或用户当前 HAR |

房间信息处理仅参考以上两个字段及路径，没有复制或执行上游脚本。活动字段只处理对象；购物字段只处理原始整数 1 或布尔 true。数值 1.0、1e0、字符串、数组、未知数字和缺失字段均保留。布尔 true 是保持类型的兼容分支，尚无当前手机展示证据；它与数字 1 一样仅在用户主动开启实验开关时生效。v1.4.1 新增的首页轮播有独立的用户 HAR 证据，见下节。

没有采用来源规则中清空全部 function_card、按 biz_id 删除未知组件、修改用户权限／会员状态或匹配其他接口的部分，也没有把公开规则里的更广匹配范围迁入本插件。

## Loon 配置依据

- [官方 Plugin 文档](https://nsloon.app/docs/Plugin/)：`[Argument]` 的 `switch,false` 默认值，以及插件参数传给 Script 的形式。
- [官方 Script 新语法](https://nsloon.app/docs/Script/script_v2/)：request/response 条件、对象参数、requires_body。新条目使用现有最低 Build 988 已覆盖的 983+ 语法。
- [官方 Script API](https://nsloon.app/docs/Script/script_api/)：读取请求／响应、以 `$done({})` 保持原响应、修改响应正文。脚本没有依赖浏览器 DOM 或第三方环境。

原生 jq 能表达简单清理，但这里要求不改变任何无关数字字面量，也没有当前 Loon 内核下 jq 长整数保真的实测。因此使用独立、无依赖的 JSON 文本定位器；完整语法校验和重复键拒绝先于区间编辑。它不递归搜索广告、不按字段名泛化删除，只精确编辑已登记的两个房间字段或首页轮播卡片区间。

## 验证分层与待核对内容

初始 v1.4.0 的本地验证只有合成数据，不是网络回放，也不是在 Loon 内核运行。v1.4.1 根据后来收到的用户 HAR 增加首页轮播处理，完成了纯本地原响应回放；新版本界面尚待更新后的手机验证。

手机待核对：当前版本是否请求该白名单接口；字段是否仍存在且类型相符；置空／关闭展示标志是否改变界面；登录与未登录、横竖屏、全屏和切房是否正常；普通弹幕、弹幕发送、关注和画质切换是否可用；以及是否与其他匹配相同接口的插件冲突。

原生礼物按钮、排行榜、PK 组件、实时消息和布局调整不在首版范围。两个实验开关默认关闭，用户更新插件不会自动开始修改直播响应。若接口或字段已经变化，先核对脱敏证据，再决定是否扩大覆盖。

## 2026-11-04 收到用户反馈与首页 HAR

最初日志截图显示 Loon 3.5.2（1005），请求统计中的 App 版本为 9.17.0。用户随后用界面截图明确目标是“直播首页”顶部大轮播，不是直播间里的房间横幅。这里的日期是收到反馈的日期，不据手机截图时间推断请求的具体日期。

- 我们的 v1.4.0 直播脚本在 app-room/v1 的 `getInfoByRoom` GET 响应上执行成功，日志为 `banner=1 shopping=0 changed=true`。这说明已登记的对象型房间字段被置空；空对象同样会计数为 1，不能据此确定原对象含有可见横幅内容。旧版本没有匹配首页 feed，不能将此日志当作首页轮播已处理的证据。
- 用户起初说购物推广消失，随后澄清无法确认此前是否存在购物推广；上述响应的购物修改计数也为 0。购物净化没有有效的界面前后对比或因果证据，此次保持购物逻辑原样，不记为验证成功。
- 另一张截图是 Biliverse.Enhanced 0.6.3 对首页导航 `x/resource/show/tab/v2` 的处理，属于不同接口，不能用来判断我们的直播字段处理，也不能据此认定插件冲突。

用户提供的 HAR 共 102 条请求。本地离线分析确认 1 个 HTTPS GET `/xlive/app-interface/v2/index/feed` 的 HTTP 200 JSON 响应；顶层成功码为数字 0，`data.card_list` 为 23 项数组：1 个 `banner_v2`、1 个 `my_idol_v1` 关注模块、1 个 `area_entrance_v3` 分区模块、20 个 `small_card_v1` 普通直播卡。第一个轮播的 `card_data.banner_v2.list` 含与截图目标一致的公开活动文案，因此确定此前遗漏的是首页接口。

v1.4.1 将原“直播活动横幅”开关扩展为“直播首页轮播/房间横幅”，仍默认关闭。首页只删除同时满足 `card_type` 字符串为 `banner_v2`、`card_data.banner_v2` 为对象且其 `list` 为数组的顶层卡片。它清理整个已登记轮播，不仅是带广告标记的轮播项，也不按活动标题判断。未知载荷结构、其他类型、关注、分区、普通直播卡、分页和其他配置不修改。JS 文件名沿用 `Bilibili-LiveClean.v1.0.js`，内部版本为 1.1.0，日志增加 `home_carousels` 数量。

独立原响应回放确认：102 条请求中仅 1 个目标响应发生处理，卡片从 23 项变为 22 项，关注／分区／20 个普通直播卡均保留；保留卡片各自原始文本、以及整个 `card_list` 数组外的原文完全相同。只开购物时首页原样放行，二次净化幂等。72 项定向合成测试和独立审阅测试（1,798 次脚本执行）另行覆盖数组删除的不同位置、连续组合、未知类型及 HTTP 边界。

分析与回放完全离线，未重放认证请求，原始 HAR、截图、URL 查询参数、账号／房间／UP 标识和令牌均不写入仓库。未将回放结果宣称为更新后的手机界面成功。下一步更新 v1.4.1 后刷新直播首页，核对轮播消失、关注与分区保留、普通直播及分页正常，再验证进房播放和弹幕互动。购物净化留待确认原本存在购物推广的同一场景单独对比，不假设缓存或其他插件冲突。
